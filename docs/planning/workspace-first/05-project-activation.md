# W05 — Activation and background ownership

**Status: complete (2026-10-06); F02–F04 closure is judged in W06.** Dependency: W04; follow the public-API design proved in W01.

## Work

1. Activate transactionally at a safe idle boundary: capture old identity/context, validate new registry/path/trust/config, prepare isolated conversation/instructions/tools, and publish selection only on success. Cancellation/failure leaves the old valid view or an explicit dashboard/blocker, never half-switched state.
2. Do not carry A's transcript, queued prompts, pending calls, summaries, compaction, or workspace navigation into B. Returning to A restores only A's validated context. Bind overlapping switches and late results to owner/generation.
3. Revalidate identity, target, moved/missing/duplicate paths, instructions, trust, configuration, and context references on activation/restore. Untrusted project extensions stay unloaded; do not load all projects' resources.
4. Retain originating-project background runs, leases, supervision, capacity, approvals, and results independently of selected view. Notify about A while B is selected without injecting A's private payload into B's model context. A's questions/quota/approvals remain decisions in A.
5. Preserve approved check definitions across candidate repair/context restore and current launch authorization through delayed start. Never change policy beneath active workers or reroute a pending A launch to B.
6. Include unknown-termination retained work in ownership/status/monitoring/shutdown. An empty active-handle list is not termination proof. Prevent duplicate coordinator acquisition when revisiting a retained run; multiple Pi sessions cannot steal selection/context/lease.
7. Separate view switching from real shutdown/reload. Maintain supervision across view replacement; real shutdown uses verified/unknown ownership rules, generation-safe cleanup, and no dispatch after safety loss. Direct-project entry stays interoperable without mixing conversations.

## Acceptance/tests

Native offline and fake-host A/B tests prove transcript/instruction/tool/path/config/approval/result/compaction isolation in the same process/interface with fixed workspace cwd. Cover cancellation and failure at activation phases, overlapping switches, queued inputs, late A results, untrusted/missing/moved B, restore, two coordinators, shared capacity, active/paused/unknown A while B selected, and shutdown/reload.

Include unknown cleanup before later watcher/lease loss, shutdown with only retained work, command substitution after repair/restore, and approval rejection between authorization and delayed startup during a switch. Final closure of all independent findings is judged in W06, not assumed here.

## Completion record

- **Implemented (`src/ui/activation.ts`, controller):** `/projects <name>` and `/workspace` switch Pi's conversation in the same process at the workspace root through command-context `newSession({ setup })`/`switchSession`. Preconditions are checked before calling Pi (interactive command context; idle with no queued input; no switch already in progress; registered, present, revalidated project — binding, repository, configuration; the project's context lock not held by another live process). A project conversation carries a `radian-project-context` tag; the private reference `<ws>/.radian/projects/<id>/state/context.json` records its context id, session file, and session id. Restore revalidates tag, workspace, registration, context id, owner, and lock; a stale, foreign, unregistered, or locked context becomes a no-tool blocked view from which `/projects` and `/workspace` still navigate. The interface's model and thinking level are carried over and re-applied (Pi itself would reset or restore them). Cancelled or failed switches clear the carry-over, release the target's lock, and leave the previous view.
- **Background ownership:** execution owners (project sessions with run, lease, supervision, coordinator) are process-wide and reused when a run is retained (no second coordinator or lease); without a run the owner is reopened to revalidate configuration, and with a run its configuration snapshot is kept (policy never changes beneath active workers). `session_shutdown` for `new`/`resume`/`fork`/`reload` only changes the view; `quit` stops owners — renewal/monitoring first, then orderly watcher release only with no live work, otherwise the watcher is left unfed so loss stops the work — and releases leases and this process's context locks. Results for A while B is shown wait in A's inbox with a payload-free notice in B and are delivered when A is shown. A per-project view lock (process identity) keeps two Pi processes — including direct entry — from holding one project's context.
- **Tests:** `tests/unit/workspace/w05-activation.test.ts` (6) — A→B→A with restore of A's own session, per-project modes, carried model/thinking, owner identity, dashboard return and prompt cwd; busy and queued-input refusal, unknown/missing projects, a live foreign lock, unloaded project resources reported; stale context restored as a blocked no-tool view with working navigation; a run retained across view changes and reload, reused on revisit, and stopped only on quit with live work leaving the watcher unfed; direct entry versus workspace lock; cancelled, failing, and overlapping switches. `tests/integration/w05-same-interface.test.ts` (native offline, real Pi RPC): dashboard → `/projects alpha` → B → A restore → `/workspace` → `/new-project demo` (exact plan in the RPC dialog; one commit by the configured identity) → restart → `/projects alpha` restoring A's transcript; each logged model request carries only the selected project's transcript, `AGENTS.md`, and working directory, while the process cwd stays the workspace root and thinking stays `high`.
- **Results:** typecheck exit 0; `npm test` 175/175; `npm run test:integration` 10/10.
- **Deferred to W06 (safety revalidation on the assembled source):** check-definition provenance across repair/context restore (F02), approval currency through delivery/delayed start including during a switch (F03), and unknown-termination retained work in monitoring/loss/shutdown (F04).
