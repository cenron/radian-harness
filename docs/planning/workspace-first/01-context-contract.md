# W01 — Supported Pi context contract

**Status: complete (2026-10-06).** Dependency: native session and clean source-worktree checks.

## Work

1. Read the workspace-first index, independent review, and installed Pi package/extension/configuration/settings/session/SDK documentation and relevant examples completely, following cross-references.
2. Identify supported public APIs for replacing project conversation context and installing selected-project instructions/tools/resources while keeping workspace `cwd` and the same interface/process. Pi 1.0.2 `newSession` has no `cwd` option; do not assume replacement reloads child project configuration.
3. Prove native offline A/B transcript/instruction isolation, cancellation/restore, and lifecycle semantics. Define how workspace navigation, queued input, compaction, skills/prompts, AGENTS.md, MCP/deferred/nested tools, settings, and project trust are isolated. Selection must not automatically change model/provider/effort.
4. Define workspace/project session types, selection generations, validated private context references, and per-project execution-owner lifetime. Native session replacement/shutdown must not accidentally stop or release background project resources.
5. Audit every reachable model execution path, including built-in/custom/nested tools, MCP/codemode, shell, and later-loaded extensions. Unknown paths fail closed. Preserve deliberate user shell controls without exposing model shell escapes.
6. Record supported APIs and an implementable design. Do not start W06 fixes as a separate prerequisite; retain the end-of-plan validation obligations.

## Acceptance

If public APIs cannot achieve option B without separate processes, private APIs, global `chdir`, or weaker guards, mark W01 blocked and stop. - **Design (implemented in W02–W05):**
  - *Sessions.* Pi's runtime `cwd` stays the workspace root. A project conversation is a Pi session created by `newSession` whose first entry is a `radian-project-context` custom entry `{ workspace, project, contextId }`; an untagged session at the root is the dashboard; Pi started inside a registered project is direct entry (Pi-native project sessions, never mixed with workspace sessions). The private reference `<ws>/.radian/projects/<id>/state/context.json` records `{ contextId, sessionFile, sessionId }`; restore requires the file, header `cwd`/`id`, and tag to match, otherwise a fresh conversation (or a blocker) is used — never another session.
  - *Activation.* Only from a command at an idle boundary with no queued messages (aborting would return queued text to the editor). The target is validated (registry, path, identity, trust/resources, config, view lock, session reference) *before* calling Pi, because a failed switch is a fatal error in interactive Pi. The interface's model and thinking level are captured and re-applied in the replacement runtime; selection never changes provider/model/effort.
  - *Lifetimes.* Each switch replaces the extension runtime, so views are per-runtime and execution owners (project sessions, leases, supervision, coordinators, notifications) live in a process-global registry keyed by workspace. `session_shutdown` `new`/`resume`/`fork`/`reload` is a view change; only `quit` is a real shutdown under the verified/unknown ownership rules. A per-project view lock (process identity) stops two Pi processes from holding the same project context; the coordinator lease still guards runs.
  - *Generations.* A process-wide selection generation increments on every activation; commands, tools, and async results capture `{ project, generation }` at invocation and resolve only against that project; late results are delivered to their owner (its view if current, otherwise its private inbox, with a payload-free notification elsewhere).
  - *Resources/trust.* The workspace runtime loads only workspace/user-trusted resources (Radian's workspace package entry). Project `.pi` resources and `.agents/skills` never load in the workspace interface; their presence is reported, and direct entry remains governed by Pi's own trust decision (Radian never writes trust). Project instructions are installed per request through `systemPromptOptions`: the files Pi would load at the project root (agent directory, ancestors, project), with project-local files re-read through the link-refusing reader.
  - *Model paths.* Allowlist only: Radian's tools plus Radian's own confined `read`/`grep`/`find`/`ls` overrides (validated per call against the captured project root, link-refusing, other projects and private state excluded); the guard also checks that each allowed name is still Radian's registration. `bash`, `powershell`, `edit`, `write`, `codemode`, `tool_search`, MCP, deferred, and other extensions' tools are blocked in every state, including nested calls. A recognized but invalid workspace is `blocked` (every tool refused), never unrestricted. User `!` commands stay a deliberate user control (run in the selected project root).
- **Limitations:** RPC/print exercise the same `AgentSessionRuntime` replacement as the TUI but not its rendering; the interactive TUI's editor/queue behavior is covered by the idle precondition, not a TUI probe. A later-loaded extension can still observe events or mutate tool input after Radian's handler (Pi does not re-validate); Radian's tool implementations revalidate inside `execute`. Read confinement is kernel-enforced for file opens; directory walks re-resolve paths and rely on the coordinator having no write path (a concurrent user edit could race them). Direct entry inherits Pi's trust semantics (a saved parent decision applies to children).
